# Repository Guidelines

## Project Structure & Module Organization
The core Cosmos-SDK application lives in `injective-chain/`, with keeper logic, specs, and module wiring under `injective-chain/modules/*` and `injective-chain/app`. Entrypoints for shipped binaries sit in `cmd/injectived` and `cmd/peggo`, while `client/` and `cli/` provide supporting CLIs. Integration harnesses reside in `interchaintest/`, shared Go utilities in `scripts/`, protobuf sources in `proto/`, and branding assets in `assets/`.

## Build, Test, and Development Commands
- `make install` builds and installs `injectived` and `peggo` with version metadata embedded.
- `./setup.sh && ./injectived.sh` bootstraps a single-validator devnet with seeded accounts for rapid local testing.
- `make lint` runs `golangci-lint` with the repo configuration; use `make lint-last-commit` for focused diffs.
- `make test-unit` executes the Ginkgo-powered unit suite; `make ictest-basic` (or other `ictest-*` targets) runs interchain regression tests.
- `make proto` regenerates protobufs and Swagger docs inside the pinned Docker builder.

## Coding Style & Naming Conventions
Format Go sources with `gofmt` before committing; the linter enforces tab-indented Go style, 140-character line guidance, and `revive` naming rules (e.g., allow `ID` suffixes, reject ALL_CAPS identifiers). Keep exported symbols documented, prefer explicit module prefixes in package names, and avoid introducing generated code outside `proto/` and `third_party`.

## Testing Guidelines
Place unit tests beside implementation files using the `_test.go` suffix and descriptive Ginkgo `Describe` blocks. Favor race-safe patterns and seed deterministic fixtures via `tests/` helpers where available. Run `make test` or `make test-unit` before submitting, and exercise at least one relevant `ictest-*` scenario when modifying cross-chain flows. Capture coverage locally with `DO_COVERAGE=true make test-unit` and attach any new coverage artifacts to review notes.

## Commit & Pull Request Guidelines
Recent history favors short, imperative summaries such as `Release of new version`; follow the same tone, optionally prefixing the primary module (`exchange: tighten margin checks`). Reference linked issues in the body, list manual test commands, and call out migrations, protobuf changes, or config bumps. Pull requests should include: concise context, screenshots for CLI/UI touches, regeneration confirmation when protobufs change, and clear rollback considerations.

## Security & Configuration Tips
Never commit keys generated by `setup.sh`; the script seeds deterministic wallets for local-only use. When tweaking protobufs, run `make proto` and commit both generated Go and Swagger artifacts. Keep environment-specific settings (e.g., `injectived.sh` flags, `config/app.toml` edits) in separate sample files so operators can diff them easily, and avoid weakening default security guardrails such as ledger support or MEMO checks without a documented rationale.
